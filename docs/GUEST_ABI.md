# Замороженный guest ABI и контракт вызова

Статус: **норма, rev 1** (2026-11-06). Нормативный владелец границы
«корпус ↔ runtime»: что именно заморожено, как идентифицируется корпус и как
устроена передача управления (диспетчер + прямые вызовы). Заменяет
`docs/ARCHITECTURE_1.27B.md` §2.2, §3.6 и блок P0-1 в §3.7 как источник
истины в вопросах ABI; измерения и лестница оптимизаций остаются в §3.7,
гейты — в `docs/VERIFICATION.md`. При расхождении приоритет у этого документа,
затем у ADR-019/ADR-022, затем у остальных.

Связанные: ADR-019, ADR-020, ADR-028, `docs/VERIFICATION.md` (V1,
V2/G-05/G-14/G-15, V4.6,
V6.2, V8), `PLAN_REFACTOR_1.27B.md` Step 5b, `docs/FILE_LAYOUT.md` (M2).
Идентификаторы `ABI-n` стабильны и не зависят от нумерации разделов.

**Причина появления.** Принцип §1.3.2 объявляет корпус дорогим неизменяемым
артефактом, а рефакторинг разрешает только выше его границы. Проверка
2026-11-06 показала, что сама граница определена неоднозначно:

1. §2.2 требует перелифта при «изменении любого поля», §3.7 разрешает
   добавление полей в конец `CPU` без перелифта, а строка ADR-019 в §11
   осталась в старой формулировке. Нормативное ядро противоречит само себе.
2. `config/layout.1.27b.json` содержит `corpus_manifest.sha256 = null`,
   `status: not_generated`, `lift_rev: 0`; при этом sha256 образов посчитаны по
   **оригинальным** PE, а Android-корпус Storm/Mss поднят с перебазированных
   (`*_a35.c`). Цепочки идентичности корпуса не существует (V4.6, G-05).
3. P0-1 объявлен «РЕАЛИЗОВАНО», но `runtime/guest/direct_call.h` объявляет
   `static` TLS-состояние в заголовке (копия на каждый TU), а
   `tools/gen_dispatch.py` генерирует независимый набор TLS. Смешанный
   direct/indirect путь не определён; заголовок включает ровно один файл —
   сам тест. Следование §3.7 сломает управление на 42 713 сайтах.

## ABI-1. Что именно заморожено

| Элемент | Правило | Перелифт при изменении |
|---|---|---|
| Поля `CPU`: имена, типы, семантика | сгенерированный C ссылается на **имена**, не на смещения | да: переименование, удаление, смена типа. **Нет**: добавление полей в конец |
| `dispatch(CPU*, uint32_t)` / `dispatch_jmp`, `void L_<va>(CPU*)` | вход по абсолютному guest VA | да |
| HLE thunk-окно `0x7F000000`, stride 16, `hle_call`, `stack_cleanup = 4 + (cdecl ? 0 : argc*4)` | адреса thunk'ов вшиты в корпус | да |
| Базы образов, identity mapping, `GVA()` | абсолютные адреса в лифте | да |
| x87 TLS, атомарности `lock xadd`/`cmpxchg` | семантика гостя | да |
| **Идиомы сгенерированного C** (`push32(ret)`, `flags_*`, развёрнутый `GVA`) | это **выход** лифтера, а не ABI; версионируется `lift_rev` + `corpus_sha256` | **нет** — перегенерация тем же лифтером, без смены баз и `layout_rev` |

Последняя строка — ключевая: P0-1…P0-6 меняют сгенерированный C и потому не
требуют «разморозки» ABI. Настоящая граница проходит по **source-level
контракту**, а не по тексту лифтнутых функций.

## ABI-2. Разрешение ADR-019 (обязательная формулировка)

ADR-019 читается так: **заморожен source-level контракт** — имена и семантика
полей `CPU`, сигнатуры `dispatch`/`dispatch_jmp`/`L_<va>`, thunk-окно, формула
снятия стека и базы образов. Добавление полей в конец `CPU` не требует
перелифта: корпус перекомпилируется при каждой сборке. Перелифт и новый
`corpus_sha256` обязаны сопровождать только переименование/удаление полей,
смену их типов, смену сигнатур, thunk-окна, формулы или баз.

Формулировка «любое изменение = перелифт» из §2.2 и строки ADR-019 **отменена**;
«потолок производительности» из §13 G6 скорректирован: после девиртуализации
и LTO компилятор удерживает guest-регистры в host-регистрах между
заинлайненными функциями без `dispatch ABI v2`.

## ABI-3. Идентичность корпуса и реестра

* **ABI-3.1** `corpus.sha256` хэширует упорядоченный набор **фактических
  входов лифта**: PE-файлы в том виде, в каком они лифтились (включая
  перебазированные Storm/Mss/Mssfast/Mp3dec), `lift_rev`, версию генератора,
  список VA и `layout_sha256`. Хэши оригинальных PE из каталога игры таковыми
  не являются (V4.6).
* **ABI-3.2** `check_layout.py` вправе считать `corpus_fixed` проверенным
  только при непустом `corpus_manifest.sha256`, совпадающем с входами; иначе
  статус гейта G-05 = `declared` (V1.3).
* **ABI-3.3** Thunk = `GUEST_HLE_BASE + slot * stride`, а `slot` выдаётся
  append-only `count++` в `hle_register_ex`. Значит **порядок регистрации
  определяет адреса импортов**. Обязателен `registry_sha256` по упорядоченному
  списку `(dll, name, ordinal, argc, flags)`; любая перестановка = новый хэш,
  новый baseline и T1. Release связывает импорты по индексу, но индекс без
  хэша порядка не является идентичностью.
* **ABI-3.4** `gen_dispatch.py` проверяет границу HLE-окна как
  `HLE_MAX * HLE_STRIDE`, а `hle_call` — как `r->count`. Это разные величины;
  thunk внутри окна, но вне зарегистрированного диапазона = fatal, а не
  молчаливый возврат (§3.6).

## ABI-4. Единое состояние переходов

**Один владелец состояния на guest thread — диспетчерский TU.** Заголовок
объявляет `extern` TLS, определение лежит ровно в одном `.c`. Объявлять
`static` TLS в заголовке **запрещено**: корпус нарезан на чанки, и каждая
копия состояния делает tail-цель из соседнего TU невидимой.

| Поле | Назначение |
|---|---|
| `depth` | глубина host-вызовов; читается и прямыми вызовами, и `dispatch_jmp` |
| `pending_valid` | есть отложенная tail-цель |
| `pending_kind` | `VA` или `FN` (указатель `L_<va>`) |
| `pending_target` | объединение VA / указателя функции |
| `draining` | re-entrancy guard drain-цикла |

Состояние thread-private (24 guest threads), **не глобальное** и не
разделяемое; синхронизация не нужна (класс `thread-private` из §3.1).
Размещение в полях `CPU` допустимо как микрооптимизация (ABI-2), но само по
себе не решает проблему разделения между TU.

## ABI-5. Смешанный прямой / косвенной путь

1. `WC3_DIRECT_CALL` увеличивает **тот же** `depth`, который проверяет
   `dispatch_jmp` в `gen_dispatch.py`. Иначе `dispatch_jmp` внутри
   девиртуализованного вызова видит `depth == 0` и уходит в рекурсию по
   host-стеку.
2. `WC3_DIRECT_TAIL` и `dispatch_jmp` публикуют цель в **один** `pending`;
   `FN` исполняется drain-циклом напрямую без hash, `VA` разрешается через
   `find_lifted` / `hle_call`. Требуется явная конверсия VA ↔ указатель.
3. `wc3_guest_leave()` дренирует на **каждой** границе прямого вызова, а не
   только на нулевой глубине: x86 `jmp` из callee возвращает управление
   caller'у, и caller не имеет права продолжить, пока tail-цель не отработала.
4. Самый внешний вход вызывает drain для косвенных `dispatch_jmp`, ещё
   идущих через legacy-диспетчер.
5. Drain — цикл с re-entrancy guard, а не рекурсия: host-стек ограничен,
   цепочка из 100 000 переходов обязана проходить.
6. `WC3_DIRECT_TAIL` в сгенерированном C сопровождается `return;`.
   `return fn(c);` в `void`-функции недопустимо по C11 6.8.6.4.
7. Цели из HLE-окна никогда не девиртуализуются (в замере 0, но правило
   обязательно). Неизвестная цель в release — fatal (§3.6, V1.3).
8. 22 197 из 42 713 конвертируемых сайтов (52%) ведут в callee с
   tail/indirect переходами — именно они требуют соблюдения пп. 1–4.

## ABI-6. Статусы честности и обязательные тесты

Используется словарь V1: `specified` (есть контракт) → `implemented` (есть
код, подключённый к корпусу) → `verified` (есть гейт). Объявленный, но не
проверяющий статус не считается зелёным (ADR-022).

| Компонент | Статус 2026-11-06 | Основание |
|---|---|---|
| legacy-диспетчер `gen_dispatch.py` | `implemented` | собственный TLS `g_disp_depth`/`g_tail_pending`/`g_tail_target` |
| `runtime/guest/direct_call.h` | **`specified`** | `static` TLS в заголовке нарушает ABI-4; включается только `tests/direct_call_test.c`; ни один сгенерированный TU его не включает |
| смешанный путь direct/indirect | `specified` | два несвязанных набора состояния; комментарий «depth is shared» неверен |
| P0-1 в целом | **`specified`, не «РЕАЛИЗОВАНО»** | 82,93% — верхняя граница статического измерения, а не реализованная оптимизация |

До перевода в `verified` обязательны тесты G-14: (a) tail между **двумя и
более TU**; (b) прямой вызов → `dispatch_jmp` в callee; (c) legacy-диспетчер →
прямой tail; (d) цепочка 100 000 переходов с контролем host-стека; (e) два
guest thread с непересекающимся состоянием; (f) golden-эквивалентность с
Python-reference лифтером; (g) release-сборка. Тест в одном TU (нынешний
`direct_call_test.c`) не может обнаружить ни (a), ни (b), ни (c).

## ABI-7. Ёмкость окна против размера реестра

Окно — 65 536 слотов по 16 Б (1 МиБ); активный реестр as-built — 4 096
записей (`HLE_MAX` в старом `hle_registry.h`). Это разные величины. Новый
скаффолд делает `#define HLE_MAX GUEST_HLE_MAX`, то есть разворачивает
`HleRegistry` на 65 536 записей ≈1,5 МБ в release плюс столько же debug-зеркала
и смешивает именно те понятия, от которых предостерегает §2.2. Требуется
явное ADR-решение: либо отдельная константа `HLE_REGISTRY_MAX`, либо
сознательное принятие 1,5 МБ. Молчаливый алиас не является решением.

## ABI-8. Полнота HLE ABI

`HleEntry` в `runtime/hle/abi/hle_abi.h` уже содержит поле `user` и
`hle_register_ex()` — устаревшее утверждение §6.1 («ещё не содержит `user`»)
отменено. Не закрыто другое: нет `result_kind`, `arg_source` и
`x87_stack_delta` (§6.2.1, §13 A2). As-built `_CIsqrt` снимает значение с
FPU-стека (меняет x87 TOP), а `cr_*_sse2` пишут результат в `c->xmm[0]`;
`hle_call` сохраняет только EBX/ESI/EDI/EBP и потому корректен лишь для
целочисленных результатов. До Step 3 обязательны симметричное сохранение
x87/SSE и golden-тест битовой точности `sqrt/pow/sin` (G2). Целевая
спецификация не имеет права быть слабее заменяемого кода.

## ABI-9. Управление изменениями

Любое изменение замороженной части — **один коммит**, содержащий
`corpus_sha256`, `layout_rev`, `lift_rev`, `registry_sha256`, обновлённый
`identity.json` (V3), пересчитанный baseline, зелёные T0+T1. Запрещено менять
ABI «заодно» с рефакторингом (§2.3.4). Изменение статуса компонента из ABI-6
проходит по V8 с evidence. Шаги, переносящие исполняемый код, блокируются
V6.2 до закрытия G-08/G-09; Step 5b дополнительно блокируется до G-14.
Пункты лестницы оптимизаций, меняющие структуру `CPU` (класс C по
`docs/PERFORMANCE_CONTRACT.md` PM-10, например P1-17 `packed eflags`), подпадают
под это правило и **не являются LiftPass**: они требуют перелифта и нового
`corpus_sha256` отдельным коммитом, даже если кажутся «просто оптимизацией».

## ABI-10. Трассировка и владельцы

| Норма | Гейт / шаг | Владелец |
|---|---|---|
| ABI-2 (ADR-019) | ревью + `check_docs.py` | Step 1, выполнено |
| ABI-3 (идентичность, порядок реестра) | G-05, V4.6 | Step 0 |
| ABI-4/ABI-5 (единое состояние) | G-14 | Step 5b |
| ABI-7 (`HLE_MAX`) | отдельное ADR | Step 3 |
| ABI-8 (`result_kind`, x87/SSE) | A2, unit-тесты | Step 3 |
| ABI-9 (управление) | V6.2, V8 | все шаги cutover |
| ABI-11 (эквивалентность сгенерированного C) | **G-15** | Step 5b |

До закрытия G-14 P0-1 не переводится в `verified` и девиртуализация не
применяется к корпусу: 42 713 сайтов — слишком большая площадь, чтобы
проверять её тестом из одного TU.

## ABI-11. Семантическая эквивалентность сгенерированного C (ADR-028)

**Причина.** ABI-1 разрешает менять сгенерированный C без перелифта, но не
определяет, чем эти изменения проверяются. `PERFORMANCE.md` требует golden-тест
для каждого LiftPass, PLAN Step 5b вызывает `tools/lift_equivalence.py`, а V2
не содержит ни одного `G-xx` для этой проверки. По V1.1/V9 такой тест не
является гейтом: переписывание 42 713 сайтов остаётся без исполнительного
контроля. Одновременно G-01 сканирует `runtime/**`, но T0 asset-free и корпуса
в нём нет, а регекс-проход по 2,4 ГБ сгенерированного C неподъёмен.

* **ABI-11.1** Эталон — Python-reference лифтер `tools/wc3skill`. Каждый pass
  сравнивает **нормализованные тела функций** (`va`, последовательность
  инструкций, видимые переходы, guest-эффекты) до и после преобразования;
  нормализация убирает имена временных переменных, форматирование и порядок
  несвязанных объявлений. Функции, которых pass не коснулся, обязаны быть
  идентичны после нормализации.
* **ABI-11.2** Каждое изменение публикует **function-level change set**
  `{va, pass_id, before_sha256, after_sha256, reason}` — легально безопасный
  артефакт без тел функций, пригодный для ревью вместо 2,4 ГБ C (BACKLOG G9).
* **ABI-11.3** Инварианты лифта проверяются **в генераторе** (EmitPass) во
  время генерации и пинятся `lift_rev` + `corpus.sha256` (BP-6.4). Линт
  сгенерированного C в T0 запрещён: G-01 проверяет рукописный `runtime/`,
  G-15 — продукт генератора.
* **ABI-11.4** Порядок: **G-14** (контракт вызова, ABI-6) → **G-15**
  (эквивалентность) → только затем pass применяется к корпусу. Цели из
  HLE-окна не девиртуализуются (ABI-5.7); `return fn(c);` в void-функции
  запрещён C11 6.8.6.4.
* **ABI-11.5** Гейт **G-15** (T0, `missing`): `tools/lift_equivalence.py`,
  golden-набор по каждому модулю, самопроверка на намеренно испорченном теле
  (V5.4), проверка пустого change set при выключенных pass'ах. Владелец —
  Step 5b (V10). Пока G-15 не `enforced`, P0-1 остаётся `specified` (ABI-6)
  и ни один pass не применяется к корпусу (V6.5).
* **ABI-11.6** Число «82,93%» снято с `war3_27_lifted.c` (10 860 из ~217 640
  функций, только `war3.exe`) и не может служить оценкой корпуса или
  основанием для ранжирования pass'ов. До G-10 (динамические счётчики) и
  G-15 ранжирование по этому числу запрещено.
