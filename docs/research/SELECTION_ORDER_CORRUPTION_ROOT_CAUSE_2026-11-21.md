# Выделение 24/40: лишние патчи, ломающие приказ и движение

**Статус:** производное исследование, rev 2 (2026-11-21), `report-only`, **не норма**.
Часть rev 1 (поведенческие гипотезы) сохранена как история. PASS_REV 52/53/54
изменили пасс; полный перелифт, сборка APK и device A/B не выполнялись.
**Предмет:** симптом «через некоторое время после игры юнит идёт не туда, как
будто выполняет точку другого юнита, затем забывает приказ; часть юнитов стоит
при выдаче приказа; при cap=12 проблемы нет».
**Исправление (2026-11-21):** `K_ORDER_CURSOR` удалён из пасса (PASS_REV 52),
глобальные хелперы и объявления удалены из runtime. PASS_REV 53 дополнительно
убрал прямой поход одиночного остатка приказа в точку. PASS_REV 54 добавил
явный список девяти third-writer continuation-фрагментов: они двигаются
вместе с контейнером, что устраняет подтверждённый stack-cookie abort.
Подробности — §8–§10.

---

## 1. Краткий вывод

Патч `selection` (PASS_REV 51, `tools/lift/csrc_local/selection.c`) делает
больше, чем расширяет ёмкости. Три группы правок **изменяют игровую логику**, а
не только размеры массивов:

1. **`K_ORDER_CURSOR` — перенос X-курсора формации через глобальные atomics**
   (commit `544a63d`, PASS_REV 49). Это единственная правка, которая
   полностью выключена при `cap=12`, ведёт глобальное состояние между
   приказами и сбрасывается только в двух из многих обработчиков приказа.
   Она объясняет все три признака сразу: чужую точку, забытый приказ и
   отложенный во времени характер сбоя. **Основной подозреваемый.**
2. **`K_ORDER_GROUP_FULL`** — порог «группа полная» перенесён с `0xC` на
   `wc3_sel_cap()`. Для 13..23 (cap=24) и 13..39 (cap=40) игра выбирает
   другую ветку `L_6F528110`, которую 1.27 писал под группы ≤12.
3. **`wc3_sel_cluster_prepare()`** — вектор членов `CPrCluster` получает
   growth-chunk 12 вместо фиксированной ёмкости; включается только при
   `cap>=24`. Это включает переаллокацию/освобождение блока, на который
   могут ссылаться другие объекты. В `SELECTION_24_ROOT_CAUSE.md §12.14`
   такой случай уже зафиксирован как **открытый**.

Дополнительно: `wc3_sel_formation_columns()` подменяет чтение 12-элементной
таблицы **выдуманной** формулой, а Rev 65 снял 15 видов guard'ов, не исправив
корень lifetime/dead-target. Это не источник чужой точки само по себе, но
повышает чувствительность к трём пунктам выше.

Ни один из «классических» подозреваемых — контейнеры записей приказа 0x24,
аппендер, доставка события юниту, host-сорт `wc3_sel_workspace_sort` — при
проверке не дал механизма порчи. Соответствующие выводы прежних ревизий
(`SELECTION_24_ROOT_CAUSE.md §0`, §7, §12.10) сохраняются.

## 2. Почему cap=12 не ломается

Почти все поведенческие хелперы имеют явную guards на cap:

| Хелпер | Guard | Поведение при 12 |
|---|---|---|
| `wc3_sel_formation_origin()` | `wc3_sel_cap() > 12u` | возвращает `base`, carry не читается |
| `wc3_sel_formation_commit()` | `wc3_sel_cap() <= 12u → return` | записи в глобал нет |
| `wc3_sel_cluster_prepare()` | `wc3_sel_cap() < 24u → return` | вектор остаётся фиксированным |
| `wc3_sel_formation_columns()` | `count <= 12u` | возвращает исходный dword таблицы |
| `INSERT_ORDER_GROUP_FULL` | `flags_sub(..., wc3_sel_cap(), 4)` | порог остаётся 12 |

То есть при 12 Corpus всё ещё 40-структурный, но все «активные» правки
становятся no-op. Это объясняет главное наблюдение пользователя: проблема
появляется только при 24/40.

## 3. Основной механизм: глобальный X-курсор формации

### 3.1. Что именно вставлено

`tools/lift/csrc_local/selection.c:1014-1031, 1087-1110, 3093-3148` — 6 сайтов
`K_ORDER_CURSOR`:

| VA | Вставка | Назначение по комментарию пасса |
|---|---|---|
| `0x6F6B9918` | `wc3_sel_formation_reset()` | сброс в прологе msg 0x13 |
| `0x6F6B9F98` | `wc3_sel_formation_reset()` | сброс в прологе msg 0x12 |
| `0x6F16A60A` | `wc3_sel_formation_origin_apply(c)` | подмена стартового X многоюнитного кластера |
| `0x6F16A5D9` | `c->eax = wc3_sel_formation_origin(c->eax)` | подмена X одиночного члена |
| `0x6F16A6C3` | `wc3_sel_formation_commit_frame(c)` | фиксация X после группы |
| `0x6F16A5E4` | `wc3_sel_formation_commit(rd32(c->ecx+0xC))` | фиксация X одиночного члена |

Хелперы в `runtime/features/selection.c:2664-2725`:

```c
static _Atomic uint32_t g_sel_formation_x;
static _Atomic int      g_sel_formation_has_x;

uint32_t wc3_sel_formation_origin(uint32_t base) {
    if (wc3_sel_cap() > 12u && atomic_load(&g_sel_formation_has_x))
        return atomic_load(&g_sel_formation_x);
    return base;
}
void wc3_sel_formation_commit(uint32_t x) {
    if (wc3_sel_cap() <= 12u) return;
    atomic_store(&g_sel_formation_x, x);
    atomic_store(&g_sel_formation_has_x, 1);
}
```

Это **продуктовое поведение**, не диагностика: вызовы не обёрнуты в
`WC3_DEBUG`, поэтому работает и в release.

### 3.2. Сброс покрывает малую долю путей, которые вызывают тот же билдер

`build/corpus-full/game/seed.c`:

- `L_6F6B98F0` (msg 0x13) — `FS_WR32` на `0x6F6B9918`, сразу за ним reset.
- `L_6F6B9F70` (msg 0x12) — `FS_WR32` на `0x6F6B9F98`, сразу за ним reset.

Но тот же самый билдер формации достигается не только из этих двух
обработчиков. Цепочка по сгенерированному C:

```
L_6F16A5B0  (билдер, где стоят origin/commit)
  <- L_6F16D990:0x6F16D9BD      (closed.c:3034864)
  <- L_6F1697A0:0x6F1697E4      (closed.c:2926378)
  <- L_6F16C54B / L_6F16CEE9    (closed.c:2798129 / 2927158)
  <- L_6F16B2F0 ( solver )      (closed.c:2638742)
  <- L_6F16C250:0x6F16C2B2      (closed.c:2446229)
```

При этом `L_6F89CBF0` — общий setter точки для приказа — вызывается
**~36 раза из ~18 функций** обработчиков msg 0x10/0x11/0x14/0x15 и
родственных путей (`closed.c:1197308, 1197411, 1197509, 1653962, 1654087,
1654212, 2018212, 2018446, 2018831, 2019214, 2297611, 2297736, 2519072,
2519541, 2697170, …`), и ни один из этих вызовов не делает reset.

Кроме того `L_6F16DD00(O, 1)` (взвод флага `0x200`, который включает solver)
вызывается из кода добавления юнитов/карты: `closed.c:16664, 17274, 810237`.
Следовательно `commit` срабатывает не «один раз на приказ», а при каждом
пересчёте кластера, включая старт карты, спавн и гибель юнитов.

### 3.3. Как это даёт именно наблюдаемый дефект

1. Групповой point-приказ (msg 0x12/0x13) делает reset, затем билдер кластера
  _commit_ит в `g_sel_formation_x` своё финальное значение X.
2. Следующий пересчёт любого другого кластера (другая подгруппа, spawn,
   автоперестроение после гибели) читает этот X через `origin()` и начинает
   раскладку **не с базовой константы `0x6FD3C744`, а с чужой точки**.
3. Юнит получает координату, рассчитанную для другого кластера/другого
   приказа → «уходит в сторону, как будто выполняет точку другого юнита».
4. `commit` тут же сохраняет новое (уже неправильное) значение; следующая
   итерация уходит ещё дальше. Отсюда **отложенный характер**: сбой
   накапливается по мере смены кластеров, а не проявляется на первом приказе.
5. Часть юнитов при этом остаётся в старом кластере/списке и не получает
   событие → «стоит при отдаче приказа», «забывает приказ».
6. При `cap=12` `origin()` и `commit()` — no-op, цепочка разрывается. 

### 3.4. Дополнительная уязвимость одиночной ветви

В `L_6F16A5B0` (`closed.c:3122782-3122785`):

```c
c->ecx = rd32((c->ebx + 0x28u));   /* база member-vector кластера */
wr32((c->ecx + 0x0Cu), c->eax);    /* записать X в member[0] */
```

`INSERT_ORDER_CURSOR_COMMIT_1` фиксирует `rd32(c->ecx+0xC)` — то есть X,
только что подставленный из carry. Если `origin` дал чужое значение,
одиночный юнит не только идёт в чужую точку, но и **перезаписывает carry**
этим значением, закрепляя ошибку для всех последующих приказов.

## 4. Второстепенные «лишние» патчи

### 4.1. `K_ORDER_GROUP_FULL` — смена ветки при ≥13 юнитах

`selection.c:1158-1170, 3297`:

```c
/* было: flags_sub(c, c->eax, 0xCu, 4); */
flags_sub(c, c->eax, wc3_sel_cap(), 4);
```

Два сайта `0x6F67DDF1` в `L_6F67DDDC`/`L_6F67DDDF` (`closed.c:2292749,
2292779`) формируют `setge` → `>= cap`. Потребитель — `L_6F680630` →
`L_6F528110` (`closed.c:438604, 1123627`), где boolean `[ebp+0x14]`
переключает ветку с дополнительной работой с `[edi+0x30]`, `[edi+0xEC]`,
`[edi+0x2A4]`. Для 13..39 юнитов игра теперь идёт по ветке, которая в 1.27
никогда не получала такие размеры. Это правдоподобный источник «приказ
не доходит / юнит стоит», но **статически не доказан** — требует A/B.

### 4.2. `wc3_sel_cluster_prepare()` — рост вместо фиксированного вектора

`runtime/features/selection.c:233-247` при `cap>=24` пишет growth-chunk `12`
в `vector+0x14`, если он нулевой. Дальше включается родной grow-путь
`0x6F16C077 → 0x6F1C5130` с realloc и free старого блока. В
`SELECTION_24_ROOT_CAUSE.md §12.14` зафиксирован crash: member-vector вырос
до 24, а `[selection+0x28]` в момент цикла приказа остался 12-элементной
базой `0x666C45C4`; 16-я запись оказалась за границей.

Текущий пасс **не содержит** исправления «обновить базу после grow»: он
только включает grow. Риск: потеря юнита из кластера → «приказ не дошёл».

### 4.3. `wc3_sel_formation_columns()` — подмена таблицы

`runtime/features/selection.c:2763-2786`. Оригинальная таблица имеет 4 блока
по 13 dword и заканчивается 바로 перед vtable `0x6FA91DF4`, поэтому её
нельзя расширить на месте. Хелпер для `count>12` возвращает:

- `3` для compact-режима;
- `ceil(count/3)` для 13..24;
- `ceil(count/4)` для 25..40.

Это **эвристика, не измеренное поведение оракула**. Значение становится
шагом батча в `group+0x12C` и определяет, какой юнит в какой строке
формации окажется. Ошибка здесь даёт «своя точка, но не та» — тот же
визуальный симптом, что и carry.

### 4.4. Rev 65: снятие guard'ов без исправления lifetimes

`SELECTION_24_ROOT_CAUSE.md §12.17`: удалены 15 видов guard'ов (24 сайта),
которые не срабатывали в успешных прогонах, но маскировали stale/dead-target.
В документе прямо указано: «корень (lifetime юнита и удаление из выделения)
не исправлен». При 24/40 юнитов stale-целей закономерно больше, поэтому
симптомы «забыл приказ / стоит» после этого стали видимыми.

### 4.5. `VA_ORDER_MSG10` (PASS_REV 51, commit `759a4e7`)

Сдвиг `[ebp-0x184…-0x160]` на `0x310`, кадр `0x17C→0x48C`, `memset
0x150→0x460` закрывает перезапис cookie в `L_6F6B95E0` (msg 0x10). Правка
новая и без device A/B; кандидат на проверку после двух описанных выше.

### 4.6. Что действительно не является причиной

| Гипотеза | Почему исключена |
|---|---|
| 12-слотовые контейнеры записей 0x24/0x20 | аппендер без проверки ёмкости, 14/14 записей записаны и потреблены (`§0`, `§7`) |
| `wc3_sel_workspace_sort()` — ошибочная транслитерация | сверено с `closed.c:2798418`: порядок swap, `key_orig` и сравнение `comiss` совпадают; отличаются только pair-смещения `0x34/0x38 → 0xA4/0xA8` |
| Handle-table free-list unlink | аргументы `L_6F1CBE60` разобраны: `[ebp+0x10]` = head, `[ebp+0x14]` = count у обоих caller'ов; вставка корректна |
| Marker в save-потоке | пишется в stream, а не в живой объект; третье dword slot 0 = `0` и в order-пути не читается |

## 5. Оставшиеся шаги проверки

Шаги 1 и 2 уже выполнены в §8 и §9; остальное требует сборки и устройства:

1. Отключить `K_ORDER_GROUP_FULL` (вернуть `0xCu`) и сравнить долю юнитов,

`sort-pre.tail == sort-post.tail`, нет `OVER` в group-трассе.

## 8. Внесённое исправление (PASS_REV 52)

Удалён **только** `K_ORDER_CURSOR` — единственная правка, для которой
статический разбор дал полную причинную цепочку от патча до симптома.
Остальные пункты §4 остаются гипотезами: их удаление либо отключает
24/40-режим (grow member-vector, таблица формации), либо меняет устоявшуюся
ветку приказа без измерений (`K_ORDER_GROUP_FULL`).

Изменены: `tools/lift/csrc_local/selection.c` (6 `VA_ORDER_CURSOR_*`, 5 блоков
вставки, 6 `case`, счётчики 6/2/4 → 0, JSON self-test 353 → 347),
`runtime/features/selection.c` (глобальные atomics и 5 хелперов),
`runtime/features/selection.h` (объявления), `tools/lift/patches/README.md`.

Возврат к базовой константе `0x6FD3C744` означает, что при разбиении выделения
на несколько кластеров их первые строки могут совпасть — это цена удаления
блуждающей точки.

**Проверено:** `selection.exe` пересобран; `--self-test` → `OK (104 sites,
idempotent, fail-closed)`; `gcc -fsyntax-only` при `WC3_DEBUG=0/1` чистый;
ссылок на удалённые символы нет; `tools/check_docs.py` — прежние 5 ошибок.

**Не проверено:** полный перелифт 263 чанков, `--verify-coverage`, сборка APK и
device A/B (сырая база не прошла предыдущие стадии пасса).

## 9. Второй дефект: 40 юнитов, часть идёт прямо в точку

**Наблюдение:** при выделении 40 и приказе «на территорию» некоторые юниты
иногда игнорируют боевой порядок и идут прямиком в целевую точку; на 24 юнитах
не наблюдалось. Проявление непостоянное.

### 9.1. Корень

Приказ разбивается на батчи. Число юнитов в батче — `min(остаток, columns)`,
где `columns` берётся из `wc3_sel_formation_columns()` и сохраняется в
`group+0x12C` (40-раскладка: `+0x1EC`). Дальше `L_6F16CF40` проверяет:

```
6F16CF60: cmp edi, 1
6F16CF63: jne general_loop
          ; special path - одиночный юнит идёт в точку приказа
```

Проверка смотрит на **размер текущего батча**, а не на размер всей группы.
Поэтому последний неполный батч из одного юнита попадает в special path и
получает координаты точки приказа вместо координат формации.

Таких юнитов может быть **несколько в одном приказе**. `L_6F16A5F8` обрабатывает
до 16 подгрупп (`ebx=0x10`, шаг `0xA4`), а `L_6F16CB80:6F16CBE0` распределяет
юнитов по ним через `(unit+0xD8)>>12 & 0xF`. Каждая подгруппа проходит
`L_6F16A6E0 → L_6F16CF40` со своим счётчиком и своим `columns`, поэтому остаток
1 возникает **в каждой подгруппе**, где count не делится на columns. При 40
юнитах нескольких типов это даёт несколько юнитов, идущих прямо в точку; при
24 подгрупп, как правило, заполнены так, что остатков нет. Исправление
`0x6F16CF60` применяется ко всем 16 подгруппам, потому что `[ecx]` — счётчик
текущей подгруппы.

Почему это почти всегда у 24 и иногда у 40:

| Режим | `columns` для 24 | остаток | `columns` для 40 | остаток |
|---|---|---|---|---|
| compact (`flag=1`) | 3 | 24 = 8×3, остатка нет | 3 | 40 = 13×3 + **1** |
| grid (`flag=0`) | 8 | 24 = 3×8, остатка нет | 10 | 40 = 4×10, остатка нет |

**непостоянный**: он возникает только в compact-режиме, когда 40 не делится
на 3 без остатка. Для 24 оба набора колонок делят группу нацело — дефект

## 10. Подтверждённый crash: stack cookie в B-обработчике (PASS_REV 54)

**Симптом (debug, 2026-11-21 11:32):** процесс `wc3.recomp.debug:roc`

`KERNEL32.dll!IsProcessorFeaturePresent`. `ra=0x6F6BBE9F` стоит сразу после
`call 0x6F78E855` (`__security_check_cookie`), поэтому это `SIGABRT` от
испорченного stack cookie, а не `SIGSEGV`. `code:139` в отчёте — статус

## 11. Диагностика: отдельный контейнер обработчика типа 0x11 (PASS_REV 55)

**Уточнение к §10.** `0x6F6BB980` — не продолжение `0x6F6BB050`, а отдельный
обработчик приказа типа 0x11. У него свой кадр `0x200`, свой cookie на
`ebp-0x10` и свой контейнер на `ebp-0x1E0`. Конструктор `0x6F6B8960`
вызывается с `this = container+0x24` и пишет capacity 12 в `[this+0x28]`
(`container+0x4C`), массив начинается с `this+0x2C` (`container+0x50`).
Пасс патчит только второй конструктор `0x6F6B8720` (`0x6F6B879A`), поэтому
у типа 0x11 остаётся 12 слотов. Девять фрагментов
`0x6F6BBD13..0x6F6BBE16` принадлежат этому обработчику; PASS_REV 54 сдвинул
их, но не сдвинул вход `L_6F6BB980` и ранние фрагменты
`0x6F6BBA2D..0x6F6BBC64`. В исходном дереве сейчас смешаны старые и новые
смещения; логирование ниже показывает это на реальном приказе до выбора
исправления.

**Что добавлено.** В `runtime/features/selection.c` — `wc3_sel_trace_h11`
(stages 0/1/3/4/5), в `runtime/features/selection.h` — объявление. Пасс
`tools/lift/csrc_local/selection.c` (PASS_REV 55) вставляет:

- вход `0x6F6BB9AE` — тип приказа, command и поля запроса;
- конструктор `0x6F6B89CB` — `this`, capacity, массив, `ret` и расстояние

Все вставки под `#if WC3_DEBUG && WC3_DEBUG_SELECTION`; в release кода нет.

`L_6F6BBD60/65`), `expected_total[K_TRACE_FORMATION]` 9 → 14; total
359 → 364. Self-test получил отдельный блок на пять вставок.

**Как читать `sel_trace.txt`.** Если 40-юнитный приказ идёт через тип 0x11:

- `h11 enter` — какой `t15` и сколько юнитов в запросе;

- `h11 append ... count=13` — переполнение 12 слотов;
- `h11 walk count=0` при непустом append — смещения входа и фрагментов
  разъехались (PASS_REV 54);
- `h11 walk count=40 room=12 over=1` — массив пишется в cookie.

## 12. Подтверждённый crash подтверждения постройки (PASS_REV 58)

**Симптом (debug, 2026-11-22):** после выбора большой группы и подтверждения
постройки процесс падал с `[crash] signal 11 at 0x100000010 (code 2)`,

происходит в обходе callback'а `L_6F28FDB0`, который останавливается только

**Корень.** Обработчик типа 0x11 `L_6F6BB980` — отдельная функция со своим
кадром `0x200` и своим контейнером на `ebp-0x1E0`. Конструктор
`L_6F6B8960` вызывается с `this = container+0x24` и пишет capacity 12 в

после 12 записей он выходил за контейнер и `L_6F28FDB0` получал

1. Вход `L_6F6BB980` и девять ранних фрагментов

3. Конструктор `0x6F6B89CB` (`L_6F6B8960`) переписывает capacity
