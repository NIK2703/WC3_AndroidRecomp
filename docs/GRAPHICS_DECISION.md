# Решение по графическому бэкенду: dual DXVK (ADR-004/007/023)

Статус: **норма, rev 1** (2026-11-06), ADR-023. Нормативный владелец раздела
`docs/ARCHITECTURE_1.27B.md` §7 в части **выбора бэкенда, селектора и
fallback**; измерения потоков vendor-кода остаются в `docs/DXVK_THREADS.md`,
гейты — в `docs/VERIFICATION.md`, границы точности — в `docs/EXACTNESS.md`.
При расхождении о выборе бэкенда приоритет у этого документа, затем у ADR.

Идентификаторы `GB-n` стабильны. Метаданные ADR-023: `{status: accepted,
date: 2026-11-06, owner: Step 7, supersedes: —}`.

**Причина появления.** §13 C1 прямо признаёт: «Dual DXVK сохранён только
потому, что уже собран». Это единственное нормативное решение (ADR-004/007),
обоснованное не измерением, а наличием артефакта. При этом §7.2 сам требует
`dxvk_shim_reset()` для fallback, которого нет; `docs/DXVK_THREADS.md` содержит
5 строк `unavailable`; а reproducible-метрика стоимости отсутствует — в
ARCHITECTURE указано 216 МБ `.so`, в ANDROID.md старого дерева ~253 МБ.
Решение имело статус `accepted` без evidence. Настоящий документ вводит
статусную честность, матрицу и критерии, при которых dual вообще оправдан.

## GB-1. Статусы ADR и честность решения

| Статус | Значение |
|---|---|
| `proposed` | решение сформулировано, не реализовано |
| `provisional` | реализовано, но **не измерено и не выбрано по данным** |
| `accepted` | поддержано evidence GB-5 и зафиксированным решением |
| `superseded` | заменено другим ADR с явной ссылкой |

* **GB-1.1** ADR-004 и ADR-007 переводятся в **`provisional`**. Их реализация
  не отменяется, но они не могут служить основанием для shipping-решения и не
  считаются доказательством (V1.2, E1.3).
* **GB-1.2** Каждый ADR обязан иметь `{id, status, date, owner, supersedes,
  evidence}` (§13 G11). Строка в таблице §11 ARCHITECTURE без этих полей
  является кандидатом, а не записью решения.
* **GB-1.3** Повышение статуса до `accepted` разрешено только после GB-5 и
  требует нового ADR с `supersedes`. Понижение строгости без ADR запрещено
  (V1.7).

## GB-2. As-built факты (проверено по исходникам и логам)

| Факт | Источник |
|---|---|
| Symbol isolation: `objcopy --prefix-symbols` по **каждому member архива** | `build_dxvk_probe.ps1:150-163` старого дерева |
| Линковка `--whole-archive libdxvk1.a libdxvk3.a --no-whole-archive`, `--exclude-libs,ALL`, статический libc++ | `build_boot_probe.ps1:584-595` |
| `dxvk_win32.cpp` (~57 КБ) архивируется **непрефиксованным внутри libdxvk1.a** → оба бэкенда делят shim и его глобалы | `build_boot_probe.ps1:424-431`, `DXVK_THREADS.md` §1 |
| Статические конструкторы **обоих** DXVK выполняются при загрузке `.so` | `DXVK_THREADS.md` §1 |
| Селектор as-built — `WC3_DXVK_VERSION=1\|3`; селектор по physical device является **целью**, а не измеренным поведением | `dxvk_entry.cpp`, `DXVK_THREADS.md` §4 |
| 2026-11-04, 2289×1080, Turnip: `Vulkan physical device 1.4 (Adreno 725)` → «DXVK 3.1.1 active», меню/credits/1v1 карта рендерятся | ANDROID.md старого дерева, блок «Verified» |
| Тот же тест, system Adreno: `Vulkan physical device 1.3` → DXVK 3.1.1 **бросает исключение** → «falling back to 1.10.3» → 1.10.3 active | там же |
| Размер: ARCHITECTURE — `libwc3game-thin.so` **216 МБ** / release APK 65,6 МБ; ANDROID.md — **~253 МБ `.so`** / ~255 МБ debug APK | разница ~37 МБ не объяснена |

**GB-2.1** Расхождение размера означает, что стоимость dual **не измерена
воспроизводимо**: ни один вариант не может быть оценён по этой метрике до
GB-5.1. Ссылаться на 216 МБ как на аргумент «и так нестрашно» запрещено.

## GB-3. Матрица решений

Ячейки заполняются только измеренными значениями; `unavailable` не является
аргументом ни «за», ни «против» (V1.2), а отсутствие измерений не превращается в
«проверено».

| Вариант | Покрытие устройств | Размер `.so` | Старт | Стабильность | Сложность fallback | Состояние shim | Evidence |
|---|---|---|---|---|---|---|---|
| **A** — только 1.10.3 + явный «устройство не поддерживается» | system 1.1–1.3, Turnip | `unavailable` | `unavailable` | `unavailable` | нет | один владелец | не снято |
| **B** — только 3.1.1 | только ≥1.3 с нужными extensions | `unavailable` | `unavailable` | падает на system Adreno 1.3 | нет | один владелец | лог 2026-11-04 |
| **C** — dual + fallback (текущий) | system + Turnip | 216 / ~253 МБ (противоречие) | `unavailable` | fallback — **штатный путь** на system-драйвере | высокая, `dxvk_shim_reset()` отсутствует | общий глобальный shim | лог 2026-11-04 + §7.2 |
| **D** — dual, ленивая загрузка одного бэкенда | system + Turnip | `unavailable` | `unavailable` | `unavailable` | средняя | изолирован | конфликтует с требованием одного `.so`, нужен отдельный ADR |

**GB-3.1** Единственная измеренная ячейка на сегодня — «B падает на system
Adreno 1.3». Вывод «значит, нужен dual» из неё **не следует**: из неё следует
лишь «B не может быть единственным бэкендом».

## GB-4. Контракт fallback (сейчас декларация §7.2)

* **GB-4.1** Ровно один бэкенд создаёт Vulkan instance/device; второй не имеет
  побочных эффектов инициализации.
* **GB-4.2** `dxvk_win32` shim **не хранит per-device состояние в глобалах**:
  потоки, sync, TLS и файлы не должны переживать смену бэкенда.
* **GB-4.3** Перед повторной инициализацией обязателен `dxvk_shim_reset()`:
  освободить instance/device/WSI, очистить state cache, сбросить thread-local
  слоты. До его реализации и device A/B **fallback не считается рабочим
  механизмом**, а §7.3 остаётся декларацией.
* **GB-4.4** Fallback однократный; `selector`/`reason`/`apiVersion` — только в
  debug. Release детерминирован и **не читает** `WC3_DXVK_VERSION`.
* **GB-4.5** Аудит статических конструкторов невыбранного DXVK: запрещены
  создание потоков, файлов, сокетов и устройств.
* **GB-4.6** Host-локи DXVK и shim'а идут по именному allowlist `--concurrency`
  и не разделяются с guest-shared объектами (§3.3); DXVK-потоки не читают
  `CPU`/HLE/handle table (DXVK_THREADS §3).
* **GB-4.7** Если оба бэкенда не создали device → явный числовой startup error
  и понятный экран в Java-ресурсах (§13 G7), а не чёрный экран.

DXVK matrix не получают статус `pass`.

## GB-6. Правило выбора и kill criterion

* **GB-6.1** Если по итогам GB-5 выигрыш 3.1.1 ограничен Turnip, а на
  system-драйвере fallback штатен, **по умолчанию выбирается A** (один 1.10.3
  + явный «устройство не поддерживается»), пока C не покажет измеренное
  преимущество, превышающее ~2× кода, время старта и сложность общего shim.
* **GB-6.2** Dual сохраняется только при измеренном выигрыше; решение
  оформляется ADR с `supersedes: ADR-004, ADR-007`. При выборе A второй архив
  удаляется из link graph, селектор и fallback упрощаются, политика `--policy`
  обновляется тем же коммитом (V1.7).
* **GB-6.3** Kill criterion (§13 G13): если к Step 9 ни A, ни C не дают
  boot → menu → map на целевом устройстве, подход пересматривается, а не
  дополняется очередным патчем WSI. Условие измеримое и имеет владельца.

## GB-7. Что не является аргументом

«Уже собрано»; «работает на одном устройстве»; debug-override
`WC3_DXVK_VERSION`; отсутствие измерений; `unavailable`, выданное за `pass`;
ссылка на ADR со статусом `provisional` как на окончательное решение;
**зелёный T1 на `gfx/null` как свидетельство работоспособности DXVK** —
headless-DUT не создаёт Vulkan instance/device и потому ничего не говорит о
матрице A/B/C/D (V4.7.3).

## GB-8. Смежные контракты (указатели)

D3D9 caps и поведение при неподдержке (§7.5, §13 C3), thread affinity D3D9 и
`D3DCREATE_MULTITHREADED` (§13 A4, E8.4), `LockRect` staging без host lock в
guest-пути (§7.5), граница C/C++ и `noexcept` (§13 G10), порядок bootstrap и
установка adrenotools-хука до libvulkan.so (E7.2), release-allowlist для
vendor-кода (§9.3), запрет внешних D3D-DLL и legacy-рендеров через `--policy`
(G-02), **headless-DUT и `gfx/null` как верификационный frontend вне APK**
(V4.7, ADR-027, BP-7.2): это не пятый кандидат и не участник GB-5.

## GB-10. Владение и пересмотр

ADR-004/007 остаются `provisional` до GB-5. Пересмотр обязателен на границе
Step 7 → Step 9 и при любом изменении link graph DXVK. Решение, принятое без
GB-5, подлежит откату как нарушающее V1.7 и E1.3.
